# Trusted operator approval adoption

Engineering permission is not brief/asset/storyboard approval. `actor_type=HUMAN` is descriptive metadata, never identity proof.

`evaluate_gates(engine, approval_verifier=verifier)` requires a trusted two-argument verifier over the exact matching `(evidence, snapshot)` for every human approval. Omitted, throwing, non-boolean or rejecting verifiers fail closed. `guard_action` passes the same verifier to gate evaluation; existing guarded actions retain their four-argument verifier contract. Integrations must implement both signatures. Test-only callbacks are never production adapters.

`approvals.SignedApprovalVerifier` implements both protocols using operator-signed Ed25519 receipts. It verifies only; it never signs, enrolls an operator or creates a signing key. Install the optional verifier dependency from `requirements-approval.txt`; a missing crypto implementation fails closed.

The trusted launcher supplies an externally pinned audience and mapping of key ID to `(operator actor ID, public key bytes)`. Never accept a key, actor allowlist, audience or permissive verifier from project/ticket data. The signer and enrollment controls must be outside agent access. A key available to the agent does not prove human approval. Enrollment/revocation remains an operator deployment prerequisite, not something an agent may declare complete.

The signing boundary must display the final subject, relevant dependency hashes and exact adoption base, and accept an explicit approval event. It signs the domain-separated canonical JSON generated by `approval_bytes(payload)`. Payload fields:

- audience, project_id, actor_id, operator_event_id, decision=`APPROVE`, issued_at (timezone-aware)
- base_state_revision and base_project_hash
- evidence: ID, kind, subject, subject_hash, dependency_hashes, status=`APPROVED`, actor_type=`HUMAN`, state_revision=`base+1`; expiry/action/provider/workspace/ticket/candidate/shot/cost fields when applicable

Envelope fields are `key_id`, `payload` and base64 `signature`. Persist only the minimum signed receipt, never private keys, credentials or raw chat. Signing a model's inferred consent is forbidden. A signature authenticates the deployed signer; it does not by itself prove that its UI/workflow was operated by a human.

`adopt_approval` checks signature, audience, project, exact base revision/hash, current subject/dependencies, expiry and duplicate event/ID. It writes only via the reserved `StateEngine.commit_approval_adoption` path with ordinary handoff evidence for Git-backed projects. It does not alter subject content, timing, assets, claims or provider state. First prepare final subject content via the normal State Engine workflow, then obtain its exact signed approval. Storyboard/animatic/final QC bindings and all typed incoming dependency edges are required. At evaluation, subject/dependency drift or trust-key revocation invalidates approval.

This implementation enables trusted adoption but does not enroll a production operator, issue a real approval, or authorize generation. Unsigned historic approvals require explicit reapproval; never auto-sign or silently normalize them.

`HUMAN_APPROVAL_ADOPTED` is reserved: generic `begin_transaction` refuses it. `adopt_approval` invokes `StateEngine.commit_approval_adoption`, which accepts only the signed envelope and trusted verifier and builds the exact approval-only delta under the writer lock. Callers cannot submit an arbitrary after-document or transition metadata. Signature/base/actor validation, revision/hash CAS, Git handoff, journal and dependency checks remain active. The event commits the exact adopted evidence hash as well as its signed payload hash.

The launcher must also inject `history_reader=engine.inspect_history` from the trusted State Engine. Evaluation requires the exact recorded `HUMAN_APPROVAL_ADOPTED` event to bind base revision/hash, resulting revision, operator event ID and signed payload hash. Missing history fails closed. A signed receipt inserted through an unrelated generic transaction cannot substitute for adoption. This establishes protocol provenance within the trusted engine; it is not a defense against an operator who can rewrite the entire repository or replace the trusted launcher.
